for 15 minutes. One run of the app's top command costs 0.71 to 0.72 s of CPU (/usr/bin/time, 3 runs: user 0.08,

raise the kernel_task alert without the window open, and happens at most once per 15 minutes, only while hot.
A cool Mac runs no top at all in menu bar mode (the measurement above: child processes are ps only).

## How we got here (measured, in order)

1. First window build: 85.8% (ps) with the window open. Profile (sample): the whole page layer was redrawn on the CPU
   every frame, plus a full layout pass each frame. Cause: continuous SwiftUI animations (sparkline glide, a 30 fps
   fan icon, bar widths animated by frame).
2. Moved the sparkline glide and the fan spin to Core Animation layers (run by the system render server),
   bars slide with an offset: 48% with the window open. Profile: numericText rolls (with blur) and bar animations,
   about 15 at once every second, still redrew the page each frame at 120 Hz.
3. Moved rolling numbers (CATextLayer push transition) and sliding bars (implicit layer animation) to Core Animation
   too. SwiftUI now draws one frame per second: 12.8% then 11.6% with the window open.
4. Menu bar only was 3.66% at first. `top` costs about 0.72 s of CPU per run (measured with /usr/bin/time: user 0.08,
   sys 0.64) and `ps` about 25 ms. Cut: `top` now runs every 15 s only while the window is open, and every 120 s
   while only the menu bar runs and the fans ramp (TopSchedule, tested). Menu bar only: 2.71%, then 2.45%.
   (Replaced in the review batch by the heating burst above.)
   The SMC key list and HID reads did not need cutting.
